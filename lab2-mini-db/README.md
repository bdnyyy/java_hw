# Лабораторная работа №2. MiniDB на Java

Упрощённая файловая СУБД для проката спортивного инвентаря. Java 8+,
консольный интерфейс, без сторонних библиотек и готовой SQL-СУБД.
Лабораторная №1 в соседней папке не изменяется.

## Возможности

- Динамические таблицы: `CREATE TABLE`, `DROP TABLE`.
- `INTEGER`, `DOUBLE`, `STRING`, `DATE`, `BOOLEAN`, а также `NULL`.
- Один непустой уникальный первичный ключ на таблицу.
- Внешние ключи с проверкой существования родителя и запретом нарушения связи
  при удалении или изменении родительского ключа.
- Одиночный и пакетный `INSERT`, необязательный список столбцов.
- `SELECT`, выбор полей, табличный вывод; `UPDATE`, `DELETE` с условием.
- `CREATE INDEX`, хеш-индекс для `WHERE column = value`, план `INDEX` / `SCAN`.
- Сериализация данных и индексов, автоматическая загрузка и сохранение каждой
  успешной изменяющей команды; резервная копия предыдущего снимка.


`out/`, `data/`, `javadoc/` создаются локально и исключены из Git.

| Класс | Ответственность |
|---|---|
| `Main` | Чтение команд, ошибки, загрузка и сохранение |
| `SQLParser` | Разбиение на токены, проверка синтаксиса, запуск операций, форматирование |
| `Database` | Repository таблиц, CRUD и общая проверка связей |
| `Table` | Схема, записи, проверка PK, выборка |
| `Column`, `Row`, `DataType` | Столбец, запись, преобразование SQL-литералов |
| `Condition` | Одно типизированное условие WHERE |
| `IndexManager` | Описание и содержимое хеш-индексов |
| `StorageManager` | DAO: чтение и безопасная запись снимков |

Данные закрыты полями `private`; схемы и списки строк доступны только для чтения.
`Row.updated()` создаёт новую запись. Перед изменением `Database` формирует
кандидатный список строк, проверяет ограничения всей базы и при ошибке возвращает
прежнее состояние. После успешной проверки индексы изменённой таблицы
перестраиваются. Так проще обеспечить их согласованность в учебном проекте.
Все строки одной SQL-команды изменяются вместе, включая пакетный INSERT.
Это не механизм многопользовательских транзакций.

Паттерны: Repository (`Database`), DAO (`StorageManager`), стандартный Iterator
коллекций Java при переборе строк. Отдельные интерфейсы и собственный итератор
не добавлены, поскольку альтернативных реализаций нет.

## Сборка и запуск

Нужен **JDK 8 или новее**, а не только JRE. Проверьте `java -version` и
`javac -version`. Команды выполняются из папки `lab2-mini-db`.

Linux / macOS:

```sh
mkdir -p out
javac -encoding UTF-8 -d out src/*.java tests/*.java
java -cp out Main
```

Windows (cmd или PowerShell; папку `out` достаточно создать один раз):

```text
mkdir out
javac -encoding UTF-8 -d out src/*.java tests/*.java
java -cp out Main
```

Консоль должна использовать UTF-8; в Windows при необходимости выполните
`chcp 65001`. Файлы исходного кода также сохранены в UTF-8.

По умолчанию данные находятся в `data/` относительно текущей рабочей папки.
Можно выбрать отдельное хранилище:

```sh
java -cp out Main data-demo
```

Вводите **одну полную команду в строке**. Завершающий `;` необязателен.
`HELP` выводит краткую справку, `EXIT` завершает работу. Конец входного потока
тоже завершает программу. При первом запуске база пуста — создайте таблицы
следующими командами. Повторно создавать их после перезапуска не требуется.

### Пример: прокат спортивного инвентаря

Каждая строка ниже — отдельная команда. Наценки, стоимость и доступность
указываются пользователем: автоматических расчётов и бизнес-правил проката нет.

```sql
CREATE TABLE equipment (id INTEGER PRIMARY KEY, name STRING, category STRING, price DOUBLE, available BOOLEAN);
CREATE TABLE rentals (id INTEGER PRIMARY KEY, equipment_id INTEGER REFERENCES equipment(id), customer STRING, start_date DATE, days INTEGER, total_price DOUBLE, returned BOOLEAN);
INSERT INTO equipment VALUES (1, 'Горные лыжи', 'Зима', 1200.0, TRUE), (2, 'Велосипед', 'Лето', 1500.0, TRUE);
INSERT INTO equipment (id, name) VALUES (3, 'Теннисная ракетка');
INSERT INTO rentals VALUES (1, 1, 'Анна Смирнова', '2026-11-12', 2, 2400.0, FALSE);
SELECT * FROM equipment;
SELECT name, price FROM equipment WHERE price > 1000;
UPDATE equipment SET available = FALSE WHERE id = 1;
UPDATE equipment SET price = 500.0, available = TRUE WHERE id = 3;
SELECT * FROM rentals WHERE start_date >= '2026-11-01';
CREATE INDEX idx_equipment_category ON equipment (category);
SELECT name, price FROM equipment WHERE category = 'Зима';
UPDATE rentals SET returned = TRUE WHERE id = 1;
UPDATE equipment SET available = TRUE WHERE id = 1;
DELETE FROM rentals WHERE id = 1;
DELETE FROM equipment WHERE id = 1;
```

`price` — цена аренды за день; `total_price` — полная стоимость конкретной аренды.
`equipment` и `rentals` связаны как 1:N. Внешние ключи реализованы в движке и
работают для любых имён таблиц, включая ссылки на ту же таблицу.

Пример табличного результата последнего SELECT до удаления:

```text
+-------------+--------+
| name        | price  |
+-------------+--------+
| Горные лыжи | 1200.0 |
+-------------+--------+
Записей: 1; план: INDEX
```

Примеры ожидаемых ошибок:

```sql
INSERT INTO equipment (id, name) VALUES (2, 'Повтор ключа');
INSERT INTO rentals (id, equipment_id) VALUES (99, 999);
INSERT INTO rentals (id, start_date) VALUES (100, '2026-02-30');
```

Удаление схемы выполняется сначала для дочерней таблицы:

```sql
DROP TABLE rentals;
DROP TABLE equipment;
```

Даже пустая дочерняя таблица запрещает DROP родительской, пока существует её
схема с REFERENCES. Для удаления отдельных строк ограничение зависит от данных.

### Поддерживаемый синтаксис

```text
CREATE TABLE name (column TYPE [PRIMARY KEY] [REFERENCES parent(key)], ...)
DROP TABLE name
INSERT INTO name [(column, ...)] VALUES (value, ...), (value, ...)
SELECT * | column, ... FROM name [WHERE column operator value]
UPDATE name SET column = value [, ...] [WHERE column operator value]
DELETE FROM name [WHERE column operator value]
CREATE INDEX index_name ON name (column)
```

Операторы: `=`, `!=`, `<>`, `>`, `<`, `>=`, `<=`, а также
`WHERE column IS NULL` / `IS NOT NULL`. Без WHERE `UPDATE` и `DELETE`
затрагивают все строки таблицы. Обычные сравнения с NULL не находят строк:
используйте `IS NULL`. Пропущенные при INSERT поля становятся NULL, кроме PK,
для которого пропуск является ошибкой.

Имена состоят из латинских букв, цифр и `_`, начинаются с буквы или `_`.
Регистр ключевых слов и имён не важен; строковые значения регистрозависимы.
Строки и даты заключаются в одинарные кавычки. Апостроф внутри строки
удваивается: `'О''Нил'`. Дата имеет формат `YYYY-MM-DD`. Дробная часть числа
отделяется точкой, поддерживается экспоненциальная запись `1e3`.
`INTEGER` — 32-битное целое, `DOUBLE` — конечное число double.

Не поддерживаются JOIN, AND/OR, ORDER BY, агрегаты, выражения, ALTER TABLE,
составные ключи, SQL-комментарии и несколько команд в одной строке. REFERENCES
записывается рядом с описанием столбца, а не отдельной секцией FOREIGN KEY.
Требуется ровно один PRIMARY KEY; имя индекса уникально в пределах базы.

## Индексы

Для каждого индексируемого столбца хранится `Map<Object, List<Row>>`:
значение → список строк. Результат сохраняет порядок вставки.

- Полный перебор: O(N) проверок.
- Индексированный поиск по равенству: в среднем O(1 + K), где K — число совпадений.
- Память индекса: O(N), без копирования самих объектов Row.
- После вставки, удаления или изменения индексы таблицы перестраиваются за O(N)
  на каждый индекс. Это осознанное упрощение; часто изменяемые большие таблицы
  лучше обслуживать инкрементальными обновлениями индексов.

Индекс используется только для `column = value` с ненулевым литералом.
Диапазоны, `IS NULL` и остальные условия используют полный перебор.
`SELECT` сообщает план, поэтому выбор алгоритма можно проверить вручную.

## Хранение и восстановление

Java Serializable сохраняет всю базу **вместе с построенными индексами** в
`data/database.dat`. Java сохраняет общие ссылки на Row, поэтому индексы после
десериализации указывают на те же записи. После загрузки проверяются типы и ключи.
Данные не исчезают при обычном выходе или перезапуске.

Сохранение после каждой успешной изменяющей команды:

1. Новый снимок записывается в `database.tmp`, поток сбрасывается, вызывается `sync()`.
2. Предыдущий основной снимок копируется в `database.bak` через временный файл.
3. Новый снимок заменяет основной через `ATOMIC_MOVE`; если файловая система
   не поддерживает эту операцию, используется обычная замена.
4. Только после сохранения пользователь получает подтверждение успеха.

Оставшийся после прерывания `database.tmp` не загружается. При повреждении или
отсутствии основного файла программа пытается восстановить `database.bak` и
показывает предупреждение. Резервная копия содержит состояние **до последней
сохранённой команды**, поэтому восстановление может потерять эту команду.
Если оба снимка повреждены, программа завершает работу с ошибкой, не подменяя
данные пустой базой. При ошибке сохранения в ходе работы загружается последнее
сохранённое состояние; если загрузка невозможна, работа прекращается.

Ограничения: один процесс на директорию данных, все данные находятся в RAM,
нет журнала WAL, блокировок и гарантии сохранности при отказе диска или потере
питания. Каталог не синхронизируется отдельно; неатомарный fallback слабее
атомарной замены. Снимки Java нельзя считать переносимым форматом между любыми
будущими версиями классов. Загружать следует только файлы, созданные этой
программой: Java-десериализация не предназначена для недоверенных файлов.

## Функциональные тесты

```sh
java -cp out DatabaseTest
```

Ожидается `PASS: 125 проверок`. Для проверки не нужен флаг `-ea` и не требуется
JUnit. Тесты используют временную директорию и удаляют её, рабочая база не меняется.
Проверяются:

- Все команды, все пять типов, все операторы сравнения и NULL.
- Пакетные операции, ошибки PK/FK и откат, защита родителя при UPDATE / DELETE / DROP.
- Неверные даты, числа, столбцы и синтаксис, кавычки и разделители внутри строк.
- Равенство результатов SCAN / INDEX, вставка, изменение, удаление и откат с индексом.
- Сохранение и загрузка индекса, резервная копия, повреждённый и отсутствующий
  основной файл, незавершённый временный файл и повреждение обоих снимков.

Проверено компилятором JDK 8 с `-Xlint:all`; тесты также запускаются на Java 21.
Документацию API можно получить командой:

```sh
javadoc -encoding UTF-8 -charset UTF-8 -d javadoc src/*.java
```

## Тестирование производительности

```sh
java -Xms256m -Xmx512m -cp out PerformanceTest 100000 500
```

Тест создаёт 100 000 записей equipment с 1000 категориями, по 100 записей
на категорию. Сравнивается выполнение `WHERE category = value` в `Table.select()`
до и после `CREATE INDEX`. Меняются искомые категории. Для каждого режима
выполняются 300 запросов прогрева, затем 7 серий по 500 запросов; берётся медиана.
Проверяются одинаковые результаты и контрольные суммы. Создание данных,
построение индекса, SQL-парсинг, файловые операции и печать результата не входят
во время поиска; построение индекса измеряется отдельно.

Измерено в облачной Linux amd64 среде на OpenJDK 1.8.0_512,
CPU AMD EPYC 9V74, виртуальной машине доступны 3 CPU, heap 256–512 MiB.

| Режим | Медиана 500 запросов, мс | Время запроса, мс |
|---|---:|---:|
| Полный перебор SCAN | 3546.662 | 7.093323 |
| Хеш-индекс INDEX | 6.970 | 0.013940 |

Ускорение в этом запуске: **508.86 раза**. Построение индекса: **64.409 мс**.
Контрольная сумма: `2596200`; результаты поиска совпали.

Микротест демонстрирует алгоритмическую разницу при селективном равенстве,
но не является универсальным тестом всей СУБД. Последовательность измерений
фиксированная: сначала SCAN, затем INDEX. На результаты влияют JIT, сборщик
мусора, загрузка виртуальной машины и доля совпадений. Если почти все строки
подходят, преимущество индекса уменьшается. Это простой учебный тест без JMH.

## Выводы

Реализована минимальная СУБД с динамической схемой, типизированными значениями,
связанными таблицами и файловым хранением. Первичные и внешние ключи защищают
данные, а проверки перед фиксацией предотвращают частичные изменения команды.
Хеш-индекс ускоряет поиск по равенству ценой дополнительной памяти и затрат
на перестроение. Снимки и резервная копия обеспечивают базовое восстановление;
для промышленной системы потребовались бы WAL, транзакции и управление
конкурентным доступом.
